## A comment pointed at a safety net that did not exist

- **What went wrong:** `src/data/drizzle/repository.ts` carried "When the first branch database is provisioned, the contract test in data/repository.contract.test.ts should be pointed at this class as well." There was no such file, and no test of any kind touched that class. 436 lines, 28 methods and 10 tables had never executed.
- **Root cause:** the comment described an intention in the grammar of a fact. "Should be pointed at" reads, months later, as a thing that exists and needs configuring rather than a thing nobody has written. Nothing links a comment to a file, so the reference could not rot loudly.
- **How it was caught:** looking for the file the comment named, while working out what already covered the repository. Had the plan been "write an integration test" rather than "find out what covers this", the comment would have been read as reassurance.
- **Proposed guide or sensor:** a comment that names a file should name a file that exists. Where the point is that something does not exist yet, say so in those words: "nothing covers this class" rather than "the contract test should be pointed at it".
- **Now enforced by:** `src/data/repository.contract.test.ts` exists, so the reference is now true. The general case is not enforced, and a link checker over comments is more machinery than this is worth.

## Postgres caught what TypeScript would have caught for free

- **What went wrong:** the first run of the contract suite against real Postgres failed with `invalid input value for enum answer_policy_mode: "truthful-gentle"`. There is no such mode. The test was wrong, not the code.
- **Root cause:** the test was written and then run straight against the database, with no typecheck in between. `AnswerPolicyMode` is a union of string literals, so `tsc` rejects it in about a second and says exactly what is wrong.
- **How it was caught:** a container, a migration and a full suite run, which is close to the most expensive way available to learn that a string literal was misspelled.
- **Proposed guide or sensor:** run the cheap check before the expensive one. After writing a test that talks to anything external, `pnpm run typecheck` rules out a whole class of failure that otherwise arrives as a confusing runtime error from another system.
- **Now enforced by:** nothing mechanical, and it needs nothing. `pnpm run check` already runs typecheck first for this exact reason. The mistake was going around it.

## Four skipped tests were one defect wearing a loop

- **What went wrong:** `e2e/room.spec.ts` had four `test.fixme` cases for night contrast, and the handoff, `docs/traceability.md` and the previous worklog all described the room screen as failing AAA at night. Only one element ever failed. The other three inherit primary ink and measure 7.12 against a target of 7.
- **Root cause:** the cases are generated by a `for` loop over four test ids and `test.fixme` applies per generated test, so skipping the one that failed meant skipping all four. After that the skip count read as the size of the problem.
- **How it was caught:** computing the real ratio for each ink before changing anything, rather than reading four skips as four failures.
- **Proposed guide or sensor:** a skipped test inside a generated loop should say in its comment which case actually fails and what it measures. Otherwise the skip count becomes a defect count and it is wrong in the direction that makes the problem look bigger.
- **Now enforced by:** the comment above that loop now states that only the location line failed and what the other three measure, and `docs/traceability.md` says the same.

## The room device was never a PWA

- **What went wrong:** PROJECT.md section 9's stack table says the room device is "a PWA in Android kiosk mode". There was no manifest and no service worker. `personas/anna-venter.md` answers the buyer's "what happens if the wifi goes down?" with "the screen keeps working", which held only while the tab stayed loaded.
- **Root cause:** the offline requirement was read as a constraint on the render path, which is how `claude/rules/room-screen.md` stated it, and that constraint was genuinely met: no fetch, no router refresh, the whole day serialised once. Nobody asked what happens on reload, and an always-on tablet reloads.
- **How it was caught:** checking for a manifest while surveying what a real room needs, rather than trusting the stack table. `docs/traceability.md` had already marked works-with-no-network as partial with the exact reason, "no test starts the room screen offline", so the gap was written down and had been read past more than once.
- **Proposed guide or sensor:** a partial row in `docs/traceability.md` that names its own missing test is a backlog item, and this one sat while three sessions worked on other things. Read that document at the start of a milestone, not only when closing a task.
- **Now enforced by:** `public/sw.js` and `e2e/room.offline.spec.ts`. Falsified before being trusted: with room caching disabled the three offline assertions fail and the manifest one still passes, so the tests depend on the thing they claim to test. The traceability row is enforced rather than partial.
